Reports a faceting or sorting parameter in solrconfig.xml that names a field which cannot serve it.

This is the one Solr inspection that guards against silence rather than against a false positive. A facet.field or sort naming a field with neither doc values nor an un-invertible index is not a subtle inefficiency — it is a request Solr refuses, so the handler carrying it answers every query with an error. Nothing in the configset says so, and the schema looks fine on its own.

Faceting and sorting read a field's values per document rather than its terms. Doc values serve them directly; an inverted index serves them only by being un-inverted into memory first, which is what uninvertible governs — and it defaults false from schema version 1.7. So a field that is perfectly searchable can be unfacetable, and the same field may deserve a warning in a facet.field and none in a qf.

Sorting needs one more thing: a single value per document. Several values have no defined order, so Solr rejects a plain sort on a multiValued field and requires a selector such as field(prices,min). That is why the warning names what the operation needs rather than asserting which part is missing — a multiValued field may have doc values and still not sort.

Five parameters are examined: facet.field, facet.pivot, sort, group.sort and group.field. Every property is resolved rather than read — from the field, then its field type, then Solr's default for the schema version. Where that cannot reach an answer, such as a field type naming a class this build has never seen, nothing is reported.

Example: <str name="facet.field">category</str> where the schema declares <field name="category" type="string" indexed="true" docValues="false"/> and <schema version="1.7">.
