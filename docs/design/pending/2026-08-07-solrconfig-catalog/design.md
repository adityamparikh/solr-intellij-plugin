# Extending the catalog to solrconfig.xml's classes and parameters

## Problem

The generated catalog knows four kinds of class, and every one of them lives in a schema.

`SolrClassKind` declares `FIELD_TYPE`, `TOKENIZER`, `TOKEN_FILTER` and `CHAR_FILTER`, and
`SolrClassKind.forTag` maps them from `fieldType`, `tokenizer`, `filter` and `charFilter` — all
schema vocabulary. Nothing in the catalog corresponds to a `<requestHandler>`, a
`<searchComponent>`, an `<updateProcessor>`, a `<queryResponseWriter>` or a `<cache>`.

**That is a fact about the generator's two discovery routes, not an oversight.**
`GenerateSolrCatalogTask` finds classes two ways, and both are schema-shaped:

| Route | What it finds | Why it stops at the schema |
|---|---|---|
| `META-INF/services/` entries matched against a fixed `analysisServices` map | tokenizers, token filters, char filters | Lucene ships SPI files naming its analysis components. Solr ships none for request handlers |
| `hierarchy.descendsFrom(it, "org/apache/solr/schema/FieldType")` | the ~40 field-type classes | Named for the one superclass a schema's `class` attribute can sit under |

So the class half of [solrconfig.xml as a first-class
surface](../2026-08-07-solrconfig-intelligence/design.md) has nothing to read.

**The parameter half has less than nothing — it has a hand-maintained list that contradicts the
specification.** `SolrConfigParser` carries sixteen parameter names across three sets:

- `BOOSTABLE_PARAMETERS` — `qf`, `pf`, `pf2`, `pf3`, `bf`, `boost`
- `SORT_PARAMETERS` — `sort`, `group.sort`
- `PLAIN_PARAMETERS` — `df`, `fl`, `facet.field`, `group.field`, `hl.fl`, `uniqueKey`,
  `facet.pivot`, `stats.field`

That list is correct and it is doing its job, because it answers a narrow question: *which
parameters hold field names*. The class's own KDoc defends the narrowness, and rightly — guessing
would produce false "no such field" warnings, which are worse than missing ones.

**But the specification's claim is the broader one**, and the broader one is not hand-maintainable:

> the parameter sets alone run to hundreds of names, and they differ between Solr lines. The
> argument that produced the factory catalog applies here with more force.

Sixteen names hand-written is fine for *does this hold a field*. It is not a basis for *what may I
write here*, which is what completion and documentation ask.

## Goals

- The catalog names the classes `solrconfig.xml` can write in a `class` attribute, per supported
  line, with the same three facts it already carries for a factory: attributes, documentation
  summary, and where the bytecode proves them, defaults and requiredness.
- The catalog names the query parameters a request handler accepts, with a documentation summary
  where Solr's own sources carry one.
- **Generated, never hand-written**, and regenerated by a version bump like everything else in
  `:generateSolrCatalog`.
- **The existing sixteen-name list keeps its job.** Whether a parameter holds a *field name* is a
  different question from whether the parameter *exists*, and the catalog answers only the second.

## Non-goals

- **Replacing `SolrConfigParser`'s field-reference rules.** Which parameters hold field names, and
  how `name^3 description` splits, stay exactly where they are. A catalog that named every parameter
  would still not say which hold fields, so folding the two would trade a correct small list for a
  large uncertain one. This record adds a population; it removes nothing.
- **Modelling parameter *values*.** `defType=edismax` has a closed set; `rows=10` does not; `bf`
  holds a function query with its own grammar. The catalog records a value's type where the bytecode
  proves it and stops there, as it already does for factory attributes.
- **Per-handler parameter scoping as a validation basis.** Knowing that `DisMaxParams` names `mm`
  does not prove `mm` is illegal in a `/select` handler configured with `defType=lucene` — Solr
  reads parameters permissively, and an unread parameter is inert rather than rejected. Scoping is
  recorded for *ranking and grouping* in a completion list, not for firing an inspection. See
  [validation is not the consumer](#validation-is-not-the-consumer-of-this).
- **The `-sources` fallback.** Unchanged: a line whose sources do not resolve ships without
  documentation rather than with hand-written prose.

## Design

### Classes: the hierarchy route, pointed at more superclasses

The field-type pass already proves the technique. `GenerateSolrCatalogTask` collects every class in
the scanned jars, builds a hierarchy, and keeps those descending from `FieldType`. Solr's
`solrconfig.xml` plugins are the same shape — a handful of well-known superclasses with concrete
implementations beneath them — so they need the same pass with more roots.

| New `SolrClassKind` | Root | Written in |
|---|---|---|
| `REQUEST_HANDLER` | `org.apache.solr.request.SolrRequestHandler` | `<requestHandler class=…>` |
| `SEARCH_COMPONENT` | `org.apache.solr.handler.component.SearchComponent` | `<searchComponent class=…>` |
| `UPDATE_PROCESSOR` | `org.apache.solr.update.processor.UpdateRequestProcessorFactory` | `<processor class=…>` |
| `RESPONSE_WRITER` | `org.apache.solr.response.QueryResponseWriter` | `<queryResponseWriter class=…>` |
| `CACHE` | `org.apache.solr.search.SolrCache` | `<filterCache class=…>` and its siblings |
| `DIRECTORY_FACTORY` | `org.apache.solr.core.DirectoryFactory` | `<directoryFactory class=…>` |
| `CODEC_FACTORY` | `org.apache.solr.core.CodecFactory` | `<codecFactory class=…>` |

**All seven roots are verified present in `solr-core-10.0.0.jar` at exactly those paths**, by listing
the resolved artifact rather than by recalling Solr's package layout. That settles the cheapest way
this table could have been wrong.

**This table should not be hand-written at all, and closing
[Q1](../2026-08-07-solrconfig-intelligence/plan.md) is what showed why.** `SolrConfig` carries
`public static final List<SolrPluginInfo> plugins`, and each entry pairs the element `tag` with the
`Class<?>` that tag's `class` attribute must implement — both plain constants in the static
initializer. So the roots are declared by the same list Solr parses `solrconfig.xml` with, and reading
them is the same pass that yields the element names.

All seven above are confirmed by it. **Sixteen more are declared that this record never listed**,
including `QParserPlugin` (`<queryParser>`), `ValueSourceParser`, `TransformerFactory`,
`QueryConverter`, `SolrEventListener`, `Expressible` and `InitParams` — so the hand-written table was
not merely fragile, it was short, which is the failure this record names two paragraphs down.

**That retires the worry rather than mitigating it.** The roots are the kind of thing that moves
between lines — this catalog already records that Solr 10 dropped four field-type classes and added
one — and the generator's standing failure mode is *producing a plausible short list rather than an
error*. A root read from `SolrConfig.plugins` cannot go quietly missing: if Solr renames or removes
one, the tag disappears from the generated list on that line and the per-kind assertion for it fails,
which is a build-time absence rather than an empty kind nobody notices. The 23 tags are **identical on
9.10.1 and 10.0.0**, verified, so the pass has a clean baseline to drift from.

The per-kind representative assertions below stay, and they are still what stands between a renamed
root and a feature that silently offers nothing — they simply now have a generated list to check
against rather than this table.

**Abstract classes and internal base classes must be excluded**, or the completion list offers
`SearchHandler`'s abstract ancestors as things to write. The existing pass does not face this
because `FieldType`'s concrete subclasses are what a schema names; here `SolrRequestHandler` has
`RequestHandlerBase` beneath it, which is real, abstract, and not writable.

### Parameters: the constant-field route, which is a third technique

The attribute pass walks a factory's `<init>` and takes the string literals passed to argument
readers. **That technique does not transfer**, and the reason is worth stating precisely: a factory
reads its attributes in its constructor, from a map handed to it at construction. A request handler
reads its parameters in `handleRequestBody` and `prepare`, from a `SolrParams` handed to it per
request — a different method, a different object, and reached through a chain of components rather
than in one body.

Following those call sites would mean interprocedural analysis across the component chain, which is
a research problem rather than a build task.

**There is a direct source, and it is the reason this is tractable at all.** Solr declares its
parameter names as `String` constants on a family of interfaces — `CommonParams`, `DisMaxParams`,
`HighlightParams`, `FacetParams`, `GroupParams`, `SpellingParams`, `TermsParams`,
`MoreLikeThisParams` and their siblings in `org.apache.solr.common.params`. A constant's *value* is
the parameter name as a configset writes it:

```
public static final String FL = "fl";
```

Those are `static final` fields with a `ConstantValue` bytecode attribute, which means **no call-site
analysis at all** — the value is in the constant pool, readable with the ASM the generator already
uses, in the same pass that reads everything else.

The interface a constant sits on also supplies a grouping for free: a name from `HighlightParams` is
a highlighting parameter, a name from `DisMaxParams` belongs to the dismax family. That grouping is
what a completion list sorts and labels by.

**This is measured, not assumed.** `javap -constants` against the resolved
`solr-solrj-10.0.0.jar` — the params interfaces live in SolrJ, not in `solr-core`, which is itself a
build change since only `solr-core` and `solr-analysis-extras` are resolved today — returns:

```
CommonParams:  Q = "q"   SORT = "sort"   START = "start"   ROWS = "rows"   FL = "fl"   DF = "df"
DisMaxParams:  QF = "qf" PF = "pf" PF2 = "pf2" PF3 = "pf3" MM = "mm" TIE = "tie" BF = "bf" ...
```

The constants are inlined, readable without call-site analysis, and cover the parameters the demo
file actually writes. The route works.

#### The contamination is real, and the obvious filter is wrong

**This record previously proposed rejecting a constant "whose value contains a space or an uppercase
letter". Dumping `CommonParams` disproves it in both directions**, which is why the filter is called
out separately rather than left as an implementation detail:

| Constant | Value | Is it a parameter? | The proposed filter said |
|---|---|---|---|
| `DEBUG_QUERY` | `debugQuery` | **yes** | reject — it has an uppercase letter |
| `RESULTS` | `results` | no — a `debug=` section name | accept |
| `QUERY` | `query` | no — a `debug=` section name | accept |
| `PING` | `ping` | no — an `action=` value | accept |
| `PING_HANDLER` | `/admin/ping` | no — a request path | accept |

A value-shape heuristic cannot separate these, because the populations are not distinguishable by
shape — `debugQuery` and `results` are both ordinary lowercase-ish identifiers and only one is a
parameter.

**So the discriminator is the interface, not the value.** `DisMaxParams` is clean: fifteen constants,
every one a real parameter. `HighlightParams`, `FacetParams` and `GroupParams` are expected to be the
same shape and must be checked one at a time. `CommonParams` is the mixed one, and it gets an
explicit exclusion list with a comment naming why each excluded constant is not a parameter.

That is more curation than this record would like — the whole argument for generating the catalog is
that hand-maintained lists go stale. **The honest position is that the exclusion list is small,
bounded, and about one interface**, which is a different proposition from hand-maintaining hundreds
of parameter names; and that a curated *interface* list is the same kind of artefact as the
`analysisServices` map the generator already carries for Lucene's SPI files. If a later reading finds
a structural signal that separates the two populations inside `CommonParams`, it replaces the list
and this paragraph.

### A fourth technique, for the elements the class routes cannot reach

The two routes above find *classes*. `solrconfig.xml` also has a vocabulary of configuration elements
that name no class at all — `<autoCommit><maxTime>`, `<filterCache size=…>`, `<requestDispatcher>` — and
a sandbox pass found the plugin exactly as silent on those as it was on everything else here.

**`EditableSolrConfigAttributes.json` is a generated source for most of them**, shipped inside
`solr-core` on both supported lines. It is a nested tree of `updateHandler`, `query` and
`requestDispatcher` carrying **40 leaf attributes**, and its type codes distinguish more than the value
type — they say whether Solr reads each one as an attribute or as a child element:

| Code | Means |
|---|---|
| `0` / `1` | string, as an attribute / as a node |
| `10` / `11` | boolean, as an attribute / as a node |
| `20` / `21` | int, as an attribute / as a node |
| `30` / `31` | float, as an attribute / as a node |

So one JSON read yields nesting, attribute names, value types **and** the attribute-versus-element
distinction, for the three subtrees where hand-editing actually concentrates. No bytecode walk, no
superclass root, no `-sources` jar.

**It is the *editable* subset, and that bound must be recorded rather than discovered.** The Config API
can only overlay what is runtime-editable, so `<config>`, `luceneMatchVersion` and `dataDir` are absent —
they are plain fields on `SolrConfig` read through `get("…")`. Those three are the elements a reader
hovers first, so they need a third source or a hand-written entry, and either way this catalog must not
imply it covers them.

### `defType`'s values fall out of the plugin roots, which retires a non-goal

`queryParser → QParserPlugin` is one of the pairs `SolrConfig.plugins` declares, so the pass that
enumerates plugin classes enumerates every registered query parser — which is exactly the closed set
`defType` accepts, per line, each with a class to document it from.

**That matters because it was declined twice.** [The intelligence
record](../2026-08-07-solrconfig-intelligence/design.md) put parameter *values* out of scope on the
strength of `bf` holding a function query, and narrowed that once already to admit field names. `defType`
is the same shape a third time: the list exists, it is derivable from a root this catalog already scans,
and refusing it costs a reader the answer. The grammars stay refused; the enumerations do not.

### Documentation: field-level Javadoc, which the extractor does not read today

The documentation extractor takes a class's *class-level* Javadoc and reduces it to its first
sentence. A parameter's documentation, where Solr writes any, is the Javadoc comment on the constant
field. Reading it is the same extractor pointed one level down, with the same ALv2 constraint and the
same decline-rather-than-guess rule.

**Expect thin returns and do not treat that as a defect.** The class-documentation work already
established the ceiling — `EdgeNGramFilterFactory`'s comment reads "Creates new instances of
EdgeNGramTokenFilter" and nothing more — and constant fields in a params interface are commented
less often than classes are. A parameter with no summary shows no summary, exactly as `StrField`
shows none.

### Validation is not the consumer of this

Worth stating in this record rather than only in the editor one, because a generated list of legal
names is exactly the shape of thing someone later points an inspection at.

The specification is explicit:

> A parameter the generator did not find is not thereby invalid; `solrconfig.xml` accepts plugin
> classes from outside Solr, and flagging what a catalog does not know would produce false positives
> on every project with a custom component.

A custom `SearchComponent` reads whatever parameter names its author chose, out of the same
`SolrParams`, and no generator will ever see them. **The catalog's parameter list is a completion
source and a documentation source. It is not a membership test.** The one validation it can support
is the narrow one the specification allows — a near-miss of a name it *does* know — and that lives in
the editor record.

### Catalog format

The TSV grows a row kind rather than a column. Class rows keep their present shape; parameter rows
carry the parameter name, its owning params interface, and a documentation summary. The existing
parser drops a row whose kind token it does not recognize, so **a catalog written by this generator
is readable by the shipped plugin without change** — the new rows are ignored until the editor side
reads them, which is what lets the two records ship in either order.

## Testing strategy

Plain JUnit 4 in `buildSrc`, as `GenerateSolrCatalogTaskTest` already is — none of this touches PSI.

- **A named representative per new kind, per supported line.** `solr.SearchHandler`,
  `solr.UpdateRequestHandler` and a `SearchComponent` implementation, asserted by name against the
  shipped catalog in the way `SolrClassCatalogTest` pins the factory trio. **Named rather than
  counted**, for the reason already recorded in Step 9: a count moves with the Solr line and fails
  for the wrong reason.
- **The abstract-exclusion case, positively.** `RequestHandlerBase` is present in the jar, descends
  from the root, and must not be in the catalog. This is the assertion that catches the pass having
  worked "well enough" to look right.
- **A parameter from each of three different params interfaces**, so a pass that found `CommonParams`
  and quietly missed the rest fails.
- **The non-parameter constants**, whichever filter is chosen: a known response-key constant is
  asserted absent, and the assertion carries a comment naming why that constant is not a parameter.
- **Both lines generate.** Solr 9 and 10 differ in this population as they do in the field types, and
  a root that exists in only one must fail loudly at generation rather than yielding an empty kind.

## Risks

- **Seven roots is seven chances to be wrong on Solr 9, and the failure is silent.** A root missing
  on a line yields zero classes of that kind, the catalog generates without error, and the editor
  feature simply never offers anything. Verified for line 10 by listing the jar; **line 9 is
  unverified**, and the per-kind representative assertions are the only mitigation that works — this
  is the exact failure `SolrClassCatalog`'s KDoc already warns about.
- **`solr-solrj` becomes a resolved artifact.** The params interfaces are not in `solr-core`, so the
  build resolves a third artifact per line. Small, but it touches `supportedSolrLines` handling in
  `build.gradle.kts` and the configuration-cache-sensitive `resolveSources` path, which the Step 9
  notes record as the awkward part of that file.
- **The `CommonParams` exclusion list is curation, and curation goes stale.** Bounded to one
  interface and required to carry a reason per entry, but a new Solr line adding a non-parameter
  constant to `CommonParams` will leak it into completion, and nothing will fail. The mitigating
  test is a total-count assertion on that one interface, which turns "a constant was added" into a
  failing build rather than a silent wrong suggestion.
- **Catalog size.** Roughly 185 entries per line today. The class additions are perhaps 60 more; the
  parameters could be several hundred. `SolrClassCatalog` loads a line's whole TSV on first use and
  caches it, which is fine at 185 and worth re-measuring at 700 — but it is loaded once per line per
  IDE session, off the highlighting path, so the expected answer is that nothing needs to change.
  Re-measure rather than assume.
- **Scope creep into `solrconfig.xml`'s non-plugin elements.** `<luceneMatchVersion>`, `<dataDir>`
  and `<autoCommit>` name no class and take no parameters. They are element vocabulary, they belong
  to the editor record, and the generator has nothing to say about them.

## Delivery

**A step in the Editor track, immediately before [solrconfig.xml as a first-class
surface](../2026-08-07-solrconfig-intelligence/design.md)**, and folded into
`specs/plans/0002-solr-intellij-plugin-plan.md` as a split of Step 9's first action — which already
names this work:

> A Gradle task that reads the Solr and Lucene artifacts per supported line and emits a catalog of
> factories, their attributes and their documentation — **and, by the same three passes, of
> `solrconfig.xml`'s plugins and their parameters.**

So this record does not add scope to the plan. It makes an existing clause of Step 9 into something
with a design behind it, and separates it from the analysis-factory work that has already shipped
under that step.

**Acceptance:** no demo step. Nothing here is visible until the editor record consumes it, which is
why the representative assertions carry the whole weight of proving it worked.
